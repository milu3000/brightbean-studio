# Explicit actions for an existing conversation owner

The conversation composer uses the existing `DMConversationOwnership`, `SendOperation`, claim fence and durable DM receipt dispatcher. It does not enroll, resume, transfer, reconcile or grant a sender access. All rollout flags remain default-off.

A new message has a new conversation action nonce. Retrying a confirmed nonce returns that receipt. A distinct explicit nonce may follow a verified own confirmed message even when the customer has not written again. Existing legacy operations retain the one-confirmed-reply-per-incoming constraint. UNKNOWN, another owner, native responder activity, identity ambiguity and history/order uncertainty still hold sends.

Owned sends require an observation token from the bounded newest canonical timeline returned to the same caller. A draft/error partial preserves the old token; a background refresh or historical page cannot renew it. The UI may apply fresh scope and availability metadata only when the newest page is actually shown and the composer revision is unchanged. The token grants no permission. Existing read permission authorizes drafting, and current send permission is checked separately at dispatch.

Before the first operation or delivery attempt, this proof may bind an existing draft to the incoming generation the person just saw. A successful reply sets waiting only if no newer incoming arrived. Once an operation exists, body, quote and observed generation are frozen in its fingerprint. A purely local unattempted operation may be explicitly retired, preserving its draft, nonce and claim history. A failed receipt may be retired only with the linked completed known-not-sent attempt. Unknown outcomes cannot be retired or retried this way.

A server-authenticated human session may create a new owner-bound action for an older verified incoming within seven days, after displaying the newest history in the current owner/control epoch. The draft, observation and operation must all postdate resume. Existing queued work is not revived and cutoffs are not changed. API, MCP and background sends retain the automated 24-hour window and resume cutoffs; request bodies cannot select human mode. Platform policy and provider acceptance remain independent of this local proof. Current account metadata does not establish Meta Human Agent feature approval or permitted purpose. Therefore this candidate holds all actual Meta manual DM sends, including legacy UI and the final provider boundary, after 24 hours with `human_agent_permission_unverified`; a two-day cutoff unit proof does not authorize or demonstrate a real extended-window send. No approval field or grant is inferred or created.

Migration `0019_owned_conversation_action` adds nullable nonce and human observation metadata to existing operations and preserves all historical rows. Reversing that migration refuses to erase populated action metadata. Rollback must use a projection/nonce-aware application with composer/dispatch flags disabled while retaining schema and receipts. This change activates no sync, retention, expiry, purge or account grants.

PostgreSQL concurrency tests cover two submissions from one rendered snapshot. SQLite tests establish state transitions only. Local provider tests use mocks and do not contact Meta.
